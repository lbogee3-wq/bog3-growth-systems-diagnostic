# Lessons learned

## About the diagnostic

1. **A diagnostic is an evidence system before it is a scoring system.** A score without traceable observations and evidence creates confidence, not understanding.
2. **System relationships matter more than category completeness.** Conversion can appear healthy while lifecycle follow-up leaks value; tools can be present while ownership is absent.
3. **Intent and completion must remain distinct.** A click, form start, scheduler view, completed booking, and retained engagement are different states.
4. **A maturity number is a conversation aid, not a finding.** Its usefulness comes from exposing assumptions, disagreements, and constraints.
5. **Calibration should precede sophistication.** Before adding a UI, database, or AI layer, test whether two people can use the anchors consistently.

## About learning Codex

1. **Ask for an executable slice.** A small end-to-end path reveals real design problems faster than a long specification alone.
2. **Preserve the failed first pass.** Comparing V1 with V2 makes the reasoning and improvement auditable.
3. **Put important judgment in inspectable artifacts.** Frameworks, schemas, formulas, tests, and examples make collaboration easier than undocumented assumptions.
4. **Use tests for meaning, not only mechanics.** The most valuable tests here protect score separation, validation, deterministic ranking, and explicit system relationships.
5. **Do not let technical expansion substitute for learning.** The next question is whether the framework produces reliable, decision-useful conversations—not whether the repository can support more features.

## Recommended next experiment

Use one de-identified real case only after defining an evidence-handling protocol. Have two assessors work independently, compare scores and reasons, record disagreements, and revise the anchors. The important result is not the average score; it is where the framework fails to produce consistent, useful judgment.
